# 模型原理说明模板批注要求

本文件整理自 `assets/模型原理说明-示例.docx` 的批注。生成模型原理说明前必须逐项执行；更换现场模板时，先使用 `scripts/extract_docx_comments.py` 重新提取批注并核对差异。

## 1. 基本信息表

- “上游接口模型编号”“下游接口模型编号”“交付时间”保持空白，不填占位符、日期或“无”。
- 模型名称必须使用命名步骤最终确定的名称，并与文档标题、正文和图中名称一致。
- “输入数据要求”和“输出数据要求”的左侧标题单元格分别向下纵向合并，覆盖该组全部文件明细行；右侧摘要行跨文件名与说明两列，后续明细行继续使用“文件名／字段说明”两列。

## 2. 算法模型简介

- 详细介绍问题背景、模块组成、数据处理链路和关键配置/输出，不只写一两句话。至少写 4 个实质段落且合计不少于 350 个中文字符。
- 适合时结合公式和符号说明计算过程；首次出现的符号必须解释含义，公式必须与当前算法一致。
- 文字和图片只保留与自主式交通系统及当前模型有关的内容，不得出现小猫、小狗等无关示例或装饰素材。
- 不出现原始论文的英文算法名、英文模型名、英文模块名及其英文全称。将模块改写为准确的中文功能名称，不直接宣称整个模型就是某个公开英文算法；保留旧文档中的设计和模块作用，但重写不符合本要求的英文命名。
- 算法名称、简介描述和课题场景必须相互对应，不拼接其他算法或其他课题内容。

## 3. 算法框架图

- 旧模型原理说明中只要存在可识别的内嵌框架图，就直接提取原图并无条件迁移，不对旧文档截图，也不做内容淘汰。
- 只有旧文档缺少框架图时才自行绘制；对新绘图继续执行不得使用论文、网页或公开资料截图的要求。
- 图中输入和输出必须与已校验测试说明的文件、数据和字段对应。
- 文件较多时，图顶端可使用真实文件名的紧凑摘要并标注总项数，完整文件名和字段仍在基本信息表中逐项列出；摘要不得改成与测试说明无关的泛化输入输出。
- 展示当前算法的主要模块、连接关系和处理方向；每个模块同时给出中文模块名和简短作用说明，不能只罗列名称。
- 框架图侧重子模块、模块职责和模块间关系，不展开成逐步数据操作清单。

## 4. 算法模型流程图

- 旧模型原理说明中只要存在可识别的内嵌流程图，就直接提取原图并无条件迁移，不对旧文档截图，也不做内容淘汰。
- 只有旧文档缺少流程图时才自行绘制；对新绘图继续执行不得使用论文、网页或公开资料截图的要求。
- 从真实输入开始，到真实输出结束，输入输出与已校验测试说明一致。
- 按顺序说明数据如何流经各模块、各模块承担什么作用、如何处理或变换数据，不能只把框架模块名称重新排列。
- 流程图侧重数据的读取、处理、传递、融合和写出，不得只是框架图的纵向版本。

## 5. 旧图无条件迁移

- 正文仍按要求使用中文功能名称，不出现原论文英文算法名、英文模型名或英文模块名。
- 旧图中的英文名称、旧模型名称、输入输出表述、图片来源和画面风格均不作为淘汰条件；已有对应旧图必须原样迁移。
- 旧图与正文的命名要求分开处理：正文继续使用最新中文名称，但不修改旧图内的文字或内容。

## 6. 生成后检查

- 移除模板批注、批注锚点、人员信息和兼容性残留。
- 检查两幅图完整写入、无文件损坏或版面裁切；旧图不要求内部名称、输入输出或中英文表述与新正文一致，新生成的缺图仍需与正文一致。
- 使用 LibreOffice 或 Microsoft Word 实际打开最终 DOCX，确认没有“发现无法读取的内容”提示。
